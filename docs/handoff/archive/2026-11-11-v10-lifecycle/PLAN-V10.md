## 2. 编排分析（第一性原理）

- **为何 A∥B 敢并行**：写面零相交（RESEARCH D9）——A 全在 `src/**`＋`verify/**`，B 全在 `setup/**`；两轨间的每个接触点（键名/形状/互斥/参数/资产名/暂存路径）已冻结为 RESEARCH §7 契约表，实现侧无协商空间；R 轨对契约表逐项双侧核对，漂移在预集成波暴露。
- **为何更新链与数据层同归 A 轨不再拆**：两者共同改写 `MaskConfig/SettingsDialog/Program`——按需求拆轨＝制造同文件多写者（AGENTS §3 大忌）；按文件归属拆轨（A=应用侧，B=安装器侧）才是真正的并行边界。轨内顺序＝先数据层根基（AppPaths）再更新链（其状态标记寄存于数据层同一键根），GOAL-V10A Phase 已按依赖排序。
- **A 快 B 慢不等价串行**：各自推送后 R 才开窗；先完成者不阻塞对方任何工作。
- **R 轨承担行为文档**：README/使用说明 的更新链/数据目录/卸载/隐私口径描述依赖 A+B 行为定型，故文档改写从 V9 的执行轨移到 R 轨（合并后写最准）；I 轨仅做版本引用联动（V9 db4947d 惯例）。
- **本轮产品代码大改**（更新器+配置层+安装器）→ 必走完整发版链（AGENTS §5）：I 轨发 v1.2.0，白名单含 VerifyUpdate 版本表联动（RESEARCH D10）。
- **V9 批次归档（D12）**：规划窗本轮已执行 git mv＋活引用改写，随本批规划文档一并提交。

## 5. 用户操作手册（怎么开执行窗口）

1. **波 1 双窗并行**：开**两个全新 ZCode 会话**（模型均 GLM-5.3、权限档「完全访问」），分别 `/goal` 粘贴 `docs/handoff/2026-11-11-v10-lifecycle/GOAL-V10A-PROMPT.md` 与 `GOAL-V10B-PROMPT.md` **完整内容**。两窗各自按其 §1 在 `OneClickBlackScreen-WorkTree\` 建本轨 worktree（命令在 GOAL 内）。**A 窗会跑 GUI 验证器注入全局键鼠——其间请勿操作键盘鼠标**；B 窗只跑 ISCC/静默安装自测，不触闸门。请勿在任一窗口工作期间手动改动仓库文件。
2. **波 2/波 3 串行**：A、B 分支都推送后（`git ls-remote --heads origin` 可见）开 R 窗（GOAL-V10R）；R 推送后开 I 窗（GOAL-V10I）。R 的八件全绿与 I 的全量验证＋真机冒烟时段同样勿动键鼠；I 轨应用内更新冒烟会真实联网下载，保持网络畅通。
3. **验收**：目标模式由独立校验器按各 GOAL「验收清单」自动核对；未达成自动续跑。
4. **红线**：AGENTS.md §5 全文适用——不删仓库、不改写远端历史、`migrate\cleanup-local.ps1` 永远由用户在旧机亲手执行、凭证不入文件。
